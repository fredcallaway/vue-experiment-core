# ADR 0002: Epoch ids are not unique over time (phases & ENavigableSequence)

- **Status:** Proposed (no decision; documenting the problem and options)
- **Date:** 2026-06-01
- **Scope:** `core/` template layer, `simplified` branch
- **Related:** [0001-remove-pseudo-leaf.md](./0001-remove-pseudo-leaf.md)
- **Relevant files:** `core/composables/useEpoch.ts`, `core/internal/composables/useEpochTree.ts`,
  `core/components/epochs/ENavigableSequence.vue`, `core/components/epochs/ESequence.vue`,
  `core/internal/local-data.ts`, `core/internal/data.ts`

## Context

The epoch system carries an implicit invariant: **every epoch has a unique id and a single
start and end.** The id is generated by `makeId` as a path through the tree
(`${parent.id}[${step}]-${name}` for children of indexable/phase epochs), and most of the
machinery assumes that id maps 1:1 to a lifecycle — one `epoch.start`, one
`setCurrentEpoch`, one `done()`/unmount.

Two constructs violate this. Depending on how you frame it, they violate uniqueness *or* the
single start/end — they are two faces of the same defect.

### `ENavigableSequence`

`ENavigableSequence` exposes `prev`/`next` so a participant can move backward and forward
through steps (`core/components/epochs/ENavigableSequence.vue`). `ESequence` renders only the
current step's child VNode (`ESequence.vue:100-104`), so navigating away unmounts a step's
child and navigating back **remounts** it. Each mount runs `useEpoch` afresh, which calls
`setCurrentEpoch` and logs `epoch.start` again (`useEpoch.ts:227-231`).

But the id is deterministic in the step (`makeId`, `useEpoch.ts:160-172`), so the remounted
child gets the **same id** as the first visit. One id, multiple start/end cycles.

### Phases (`usePhaseEpoch`)

A phase epoch can loop (ADR 0001 calls out the looping `choice`/`durian` phases and
`goTo(0)`). Re-entering a phase calls `enterPhaseChild()` again, which does
`makeEpoch({ name: phase, parent: E })` and logs `epoch.start`
(`useEpoch.ts:328-335`). The id `…[<phase>]-<phase>` is a function of the phase name only, so
the re-entry reuses the same id with a fresh start.

### Two framings of one defect

- **"Unique id, but many starts/ends."** The id is stable; the epoch is entered and exited
  repeatedly. This violates *single start/end*.
- **"Distinct visits, but shared id."** Each pass through a step/phase is a genuinely distinct
  episode of behavior, but they are indistinguishable in data and as jump targets. This
  violates *uniqueness*.

Both reduce to: **the id is a function of position in the tree, but lifecycle is a function of
visitation.** The two were assumed to coincide; in navigable sequences and looping phases they
do not.

### Evidence the system already half-knows this

- `makeEpoch` registers a child only if no existing child shares its id
  (`useEpoch.ts:112-116`). The comment attributes this to "backward navigation in navigable
  sequences" — i.e. the dedup exists *precisely because* ids recur. It reads like a guard but
  is really a designed accommodation of non-unique ids.
- `jumpToEpoch` short-circuits when `_currentEpoch.id === epochId` ("already at target")
  (`useEpoch.ts:383-386`) and the outline (`useEpochTree.ts`) is a static tree of positions —
  both are already location-keyed and behave correctly under recurrence.

### Where it actually bites: data attribution

The one place that silently loses information is **logging**. `epoch.start` is used as a
running marker that stamps every subsequent event with the current epoch:

- `local-data.ts:215-217` (`makeEventList`) sets `currentEpoch = payload.id` on each
  `epoch.start` and attaches it to every following row.
- `data.ts:120-128` (`decompressEvents`) does the same to reconstruct `currentEpochId`.

So all logged behavior is attributed to an epoch **by id alone**. When a participant visits
step 2 twice (or a phase loops), both passes emit `epoch.start` with the same id and both
sets of events are attributed to that one id, with no way to order or separate them.

## Problem statement

Decide whether the "unique id + single start/end" invariant is worth preserving, and if not,
how to make the data faithful to a world where an epoch can be entered multiple times.

## Options

### A. Keep the invariant — idempotent re-entry

Treat a revisit as re-activating the *same* epoch rather than creating a new one: reuse the
existing epoch object, suppress the duplicate `epoch.start`, and re-`setCurrentEpoch` it.

- **Pros:** Restores the clean 1:1 invariant; downstream consumers need no changes.
- **Cons:** Throws away real information — the fact that the participant actually returned to a
  step and re-engaged with it is no longer in the data. Requires reuse logic across mount
  cycles (the epoch object must outlive unmount). Fights the natural Vue mount/unmount flow
  that currently drives `useEpoch`.

### B. Visit-scoped ids

Make the id encode the visit, e.g. `…[2]-page#0`, `…[2]-page#1`. Every entry is a genuinely
distinct, uniquely-identified epoch.

- **Pros:** Restores uniqueness; each pass is independently addressable and analyzable.
- **Cons:** The outline tree (positions) and jump targets become ambiguous — "jump to
  `…[2]-page`" must resolve to *some* visit (latest? a specific one?). Spreads a visit suffix
  through `makeId`, `jumpToEpoch` parsing, and the outline. Outline nodes are positions, not
  visits, so the two concepts now disagree on what an id means.

### C. Separate position id from instance id

Keep a stable position-id for outline/jump, and add a separate per-visit instance id used for
logging. Don't conflate "where in the tree" with "which pass."

- **Pros:** Most faithful to both needs; outline/jump stay location-keyed while data
  distinguishes visits.
- **Cons:** Introduces a second identifier concept that must be threaded through the logging
  path and understood by analysis code. Largest surface area.

### D. Redefine the invariant — id is a tree location; count instances at start

Stop treating uniqueness-over-time as the invariant. **An id identifies a location in the
epoch tree and may be entered/exited multiple times.** Each entry is an *instance*, and
`epoch.start` carries an instance counter so analysis can distinguish (and order) visits.

This ratifies what the code already does — the `makeEpoch` dedup, the location-keyed
outline/jump — rather than fighting it. The only producer that needs to change is the
`epoch.start` log; the consumer side already funnels through two spots
(`makeEventList`, `decompressEvents`) that stamp events with the current epoch and could carry
`(id, instance)` instead of `id`.

- **Pros:** Smallest change; aligns the stated invariant with actual behavior; preserves the
  information that a revisit happened; outline/jump untouched.
- **Cons:** Requires deciding the counter's semantics (see below); `(id, instance)` becomes the
  real key for event→epoch attribution, so any analysis that assumed one `epoch.start` per id
  must adapt.

#### Counter semantics (the one real sub-decision for D)

A per-id counter incremented on each entry, stored module-level (survives unmount; reset per
page / experiment load). The question is *what counts as an entry*:

| | "Entry count" (per start) | "Logical visit" (per deliberate pass) |
|---|---|---|
| Increment on | every `useEpoch` / `enterPhaseChild` | only participant-driven revisits |
| HMR remount | bumps (noise) | should not bump |
| jump re-entry | bumps | arguably should not bump |

The simplest honest choice is **entry count**: every start logs an incrementing `instance`.
It is truthful (each really is a fresh lifecycle) and trivial. The cost is that HMR- and
jump-driven re-entries also increment, so `instance` means "i-th time this position was
entered," not "i-th deliberate participant visit." Filtering can be added later if analysis
needs the stricter notion.

## Recommendation (non-binding)

If we act at all, **Option D** is the lowest-cost path and the one most consistent with the
existing code, which already treats ids as locations everywhere except the `epoch.start` log.
The work is: (1) add an instance counter to the two `epoch.start` call sites, (2) carry
`(id, instance)` through `makeEventList`/`decompressEvents`, (3) document on `Epoch.id` /
`makeId` that ids are tree locations, not unique over time. No outline or jump changes.

We may also choose to **do nothing**: the defect is confined to data attribution for revisited
steps and looping phases, and experiments that don't use `ENavigableSequence` or looping
phases are unaffected.

## Open questions

- Do any current experiments rely on `ENavigableSequence` revisits or looping phases in a way
  that already produces ambiguous data? (Worth checking the example projects before committing.)
- For Option D, is "entry count" sufficient for analysis, or is "logical visit" needed?
- Should `epoch.done` also carry the instance, for symmetric pairing of start/end in the log?
